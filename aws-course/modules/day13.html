Weekend Project: A Secure Two-Tier Network with Monitoring

By the end of today you can Combine Week 1 and 2 into one architecture: a web server in a public subnet, an app server hidden in a private subnet, least-privilege security groups, an alarm that emails you when CPU spikes, and a billing guard. You'll also document it as a portfolio piece.

1. The target architecture

2. Concept first: CloudWatch in 5 minutes

CloudWatch collects metrics (numbers over time such as CPU), logs, and fires alarms that trigger actions like an email through SNS (Simple Notification Service).

Analogy: a car dashboardMetrics are the gauges. The alarm is the warning light plus a buzzer. SNS is the buzzer wired to your phone.
  • EC2 reports basic metrics every 5 minutes free (1 minute with detailed monitoring, paid). It does not report memory or disk usage unless you install the CloudWatch agent.
  • Alarm states: OK, ALARM, INSUFFICIENT_DATA.
  • EventBridge reacts to events ("instance stopped") and schedules tasks like cron.

3. Project steps (aim for 3 hours)

Cost safetyTwo small instances for a few hours is fine. No NAT gateway in this project. Terminate everything at the end.
  1. Network (reuse Day 8): day8-vpc with day8-public-a (has IGW route) and day8-private-b (no IGW route). Verify in the VPC Resource map.
  2. Security groups: web-sg: HTTP 80 from anywhere, SSH from My IP. app-sg: TCP 8080 and SSH only from web-sg.
  3. App tier: launch app in the private subnet, no public IP, with user data that serves something on 8080: 
    #!/bin/bash
mkdir /srv/app && echo '{"status":"ok","tier":"app"}' > /srv/app/health.json
cd /srv/app && nohup python3 -m http.server 8080 &
  4. Web tier: launch web in the public subnet with nginx (Day 5 user data). SSH in and prove tier-to-tier access: 
    curl http://APP_PRIVATE_IP:8080/health.json   # works: from web-sg
# from your laptop the same IP is unreachable. That's the point.
  5. Reverse proxy (stretch goal): on web, configure nginx location /api/ { proxy_pass http://APP_PRIVATE_IP:8080/; } and test http://WEB_IP/api/health.json from your laptop. This is how real two-tier apps work.
  6. Monitoring: SNS → Create topic day13-alerts → create an email subscription and confirm it from your inbox. CloudWatch → Alarms → Create alarm on CPUUtilization of web, threshold > 60% for 1 datapoint, action = your SNS topic.
  7. Trigger the alarm: on web run for i in 1 2; do (timeout 600 sh -c "while :; do :; done" &); done (two busy loops for 10 minutes; no install needed). Within ~5-10 minutes the alarm goes red and an email arrives. Stop it early with pkill -f "while :".
  8. Review security: run IAM → Access Analyzer or check Trusted Advisor for open ports. Verify root MFA is on and you have a budget alert (Day 2).
  9. Document it. In the repo create aws-course/labs/week2-architecture.md containing: the diagram above (redrawn in your own words), the security group table, what you'd change for production (e.g., two AZs, a load balancer, HTTPS), and 5 sentences on what confused you.
  10. Cleanup: terminate both instances, delete the alarm and SNS topic. Leave the VPC (free).

4. Exam notes

Remember
  • Tiering = security + scaling boundary. Public tier minimal, data tier private.
  • CloudWatch alarms can notify (SNS), scale (Auto Scaling), or act on EC2 (stop/reboot/recover).
  • Memory metrics need the CloudWatch agent.
  • AWS Well-Architected has six pillars: Operational Excellence, Security, Reliability, Performance Efficiency, Cost Optimization, Sustainability.

5. Quiz

Q1. How do you let only the web tier talk to the app tier?App security group allows the port with source = web security group.
Q2. Which service sends the email when an alarm fires?SNS (Simple Notification Service).
Q3. Why can't CloudWatch show EC2 memory by default?Memory is inside the guest OS; AWS only sees hypervisor-level metrics. Install the CloudWatch agent.
Q4. Name three Well-Architected pillars.Any of: Operational Excellence, Security, Reliability, Performance Efficiency, Cost Optimization, Sustainability.
