Weekend Project: A Secure, Monitored Web App

By the end of today you will have A real mini-architecture in your own account: a web server in a custom VPC, locked-down firewalls, an IAM role instead of keys, a CloudWatch alarm, a budget guard and an architecture diagram you can show on GitHub or in an interview.

1. The brief

You are the cloud engineer for a small business that wants a website. Requirements: reachable from the internet on HTTP only, admin access only from your IP, no access keys stored on the server, alerts if it overloads, and spend capped at about USD 5. Everything you need was taught in Days 1–12. Resist copy-pasting; try each step from memory, then peek at the hints.

2. Build steps (try first, hints below)

  1. Budget: create a monthly Budget of USD 5 with email alerts at 80%. (Day 2)
  2. Network: VPC, public subnet, IGW, route table. (Day 9)
  3. Bucket: a private S3 bucket holding site.html. (Day 6)
  4. IAM role for EC2 with read-only access to that one bucket: write a custom least-privilege policy limited to s3:GetObject on arn:aws:s3:::YOUR-BUCKET/*. (Day 3)
  5. Security group: HTTP from anywhere, SSH from your IP only.
  6. Launch EC2 with the role attached and user data that pulls the page from S3 using the role (no keys!): 
    #!/bin/bash
dnf install -y nginx
aws s3 cp s3://YOUR-BUCKET/site.html /usr/share/nginx/html/index.html
systemctl enable --now nginx
  7. Observe: SNS topic + CPU alarm like Day 12.
  8. Verify like an auditor: in CloudTrail find the RunInstances event and the instance's use of the role (AssumeRole).
  9. Attack your own work: (a) try opening port 22 from the internet in a browser: it should hang; (b) try an aws s3 ls of a different bucket from the server: it must be AccessDenied. That proves least privilege works.
Hint: least-privilege policy JSON 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::YOUR-BUCKET/*"
  }]
}
Hint: page doesn't load?Run the Day 9 troubleshooting checklist. Also check sudo cat /var/log/cloud-init-output.log on the server to see if user data failed.

3. Document it (this is what employers see)

In aws-course/labs/week2-project/ create a README.md with: the diagram, what each component does and why, the cost you incurred, and 3 things that went wrong and how you fixed them. Add screenshots under evidence/.

4. Cleanup (non-negotiable)

Terminate EC2, delete alarm/SNS, bucket (empty first), role/policy, VPC. Keep the Budget. Next morning check Billing → Bills for stray items.
