Watching and Governing: CloudWatch, CloudTrail, Config, Organizations (Weekend Lab)

By the end of today you can Tell CloudWatch, CloudTrail and Config apart, build an alarm that emails you when a server is overloaded, trace "who did what" in your account, and explain how companies govern hundreds of accounts with Organizations.

1. First principles: running something means watching it

Three different questions come up when something goes wrong, and AWS has one service for each:

QuestionServiceAnalogy (a building)
How is it performing right now? (CPU, errors, logs)CloudWatchThe dashboard of sensors: temperature, power usage, alarm bell
Who did what, and when? (API calls)CloudTrailThe CCTV and visitor logbook at reception
What does it look like, and does it follow the rules? (configuration history)ConfigBuilding inspector comparing the layout with the approved plan, keeping old snapshots

Key facts

  • CloudWatch collects metrics (EC2 CPU every 5 min by default; 1 min with detailed monitoring). Memory and disk usage are not collected by default, you need the CloudWatch agent. Alarms trigger actions: notify via SNS, auto-scale, reboot. Logs store app output. EventBridge reacts to events ("when an instance stops, run this").
  • CloudTrail is on by default with 90 days of Event history (management events). For longer retention create a trail delivering to S3. Remember: it records API calls, whether from console, CLI or SDK.
  • Config records resource configuration changes and evaluates rules ("S3 buckets must not be public", "volumes must be encrypted").

Governing many accounts

AWS Organizations groups accounts in a tree of organizational units, gives consolidated billing (one bill, combined volume discounts) and lets you attach Service Control Policies (SCPs) that set the maximum permissions any account (even its admin) can have.

Analogy: a school groupOrganizations is the head office of a school chain. Each school (account) has its own principal (admin), but head office's rulebook (SCP) says "no school may ever set up a branch outside the country", whatever the principal wants. SCPs limit, they never grant by themselves. IAM still has to allow the action.

2. Lab A: alarm + email when a server is overloaded (60 min)

  1. Create a notification topic: SNS → Topics → Create Standard topic lab-alerts → Create subscription: Protocol Email, your email → open the confirmation email and click Confirm subscription.
  2. Launch a t3.micro (any lab VPC or the default one) with Amazon Linux 2023 and an SSM role (Day 10) so you can use Session Manager.
  3. Create the alarm: CloudWatch → Alarms → Create alarm → Select metric → EC2 → Per-Instance Metrics → your instance → CPUUtilization. Statistic Average, period 1 minute. Condition: Greater than 60; Datapoints to alarm 2 out of 2. Next → Action: In alarm → select lab-alerts. Name lab-high-cpu.
  4. Cause the fire: connect with Session Manager and run 
    sudo dnf install -y stress-ng 2>/dev/null || sudo dnf install -y stress
stress-ng --cpu 2 --timeout 600s &     # or:  yes > /dev/null &   (run twice)
  5. Watch the alarm go OK → In alarm (3–6 min) and receive your email. Stop the load (pkill stress-ng or pkill yes); watch it return to OK.
  6. Bonus: add a second alarm that reboots the instance on StatusCheckFailed_System (alarm action → EC2 recover). This is how "self-healing" starts.

3. Lab B: be your own detective with CloudTrail (30 min)

  1. CloudTrail → Event history. Filter Event name = RunInstances. Open your launch above: see userIdentity, sourceIPAddress, userAgent (console vs CLI) and the parameters. Anyone in your account doing anything leaves such a record.
  2. Filter by User name = root. If you see root activity other than setup, ask yourself why.
  3. Create a trail (lab-trail, all Regions, new S3 bucket). The first copy of management events is free but S3 storage costs pennies. After 10 minutes, find the JSON.gz logs in the bucket. This is the evidence an auditor wants.

4. Lab C: AWS Config and a rule (30 min, optional but valuable)

  1. Config → Get started → Record all resources (costs a little; stop recording afterwards).
  2. Add the managed rule s3-bucket-public-read-prohibited and encrypted-volumes. See which resources are Non-compliant (your old default-VPC volumes might be).

5. Cleanup (important)

  • Terminate the EC2 instance; delete the alarms and the SNS topic.
  • CloudTrail: delete lab-trail and empty/delete its bucket (unless you want to keep one real trail; one is a good habit).
  • Config: stop recording and delete the recorder/rules.

6. Exam notes

Remember
  • CloudWatch = monitor; CloudTrail = audit API calls; Config = config history & compliance.
  • EC2 basic monitoring 5 min; detailed 1 min. No memory metric by default.
  • SNS delivers notifications; EventBridge routes events to targets.
  • SCPs never grant permissions (they only set the ceiling) and don't apply to the management account.
  • Consolidated billing = one bill + pooled discounts.
  • Trusted Advisor = best-practice checks across 5 categories; Health = outages affecting you.

7. Quiz

1. Who deleted the S3 bucket yesterday?CloudTrail.
2. Notify me when CPU stays over 80%?CloudWatch alarm → SNS.
3. Detect when a security group is changed to allow 0.0.0.0/0 on port 22, and check compliance over time?AWS Config (rule), with CloudTrail showing who made the change.
4. Prevent all accounts in the organization from using a certain Region?An SCP in AWS Organizations.
5. Where do you see recommendations to cut cost and close security gaps?AWS Trusted Advisor.
6. Which metric isn't collected for EC2 without an agent?Memory (RAM) utilization.
7. What gives you a single bill for many accounts?Consolidated billing in AWS Organizations.
