Monitoring, Billing Tools and the Well-Architected Framework

By the end of today you can Set a CloudWatch alarm that emails you, know which tool answers which cost/monitoring question, name the Support plans, and recite the six Well-Architected pillars.

1. First principles: you can't fix what you can't see

Analogy: a car dashboardCloudWatch metrics are the gauges (speed, fuel). Logs are the black-box recorder. An alarm is the warning light. SNS is the horn that actually wakes you. CloudTrail (Day 11) is the CCTV showing who touched the car.
ServiceAnswers
CloudWatch MetricsHow busy is it? (CPU, network, disk I/O). EC2 basic = every 5 min, detailed = 1 min. Memory and disk-space are NOT default metrics: install the CloudWatch agent.
CloudWatch LogsWhat did the app say? (collects logs from servers, Lambda…)
CloudWatch AlarmsTell me/do something when a metric crosses a line (notify, auto scale, reboot)
EventBridgeWhen X happens (an instance stops, a schedule fires) trigger Y
SNSPublish a message to many subscribers (email, SMS, Lambda)
CloudTrailWho made which API call?

Support plans (changed recently, verify at the link)

AWS now sells Basic (free for everyone: docs, forums, core Trusted Advisor checks, Health Dashboard), Business Support+ (24/7 access to AWS experts, minimum about USD 29/month per account), Enterprise Support, and Unified Operations (for mission-critical workloads). The older Developer, Business and Enterprise On-Ramp plans are being retired, but older exam guides and practice tests still use those names, so learn both: Developer (business hours email) → Business (24/7, full Trusted Advisor) → Enterprise (TAM, fastest response). Check aws.amazon.com/premiumsupport/plans and the current CLF-C02 exam guide.

3. The Well-Architected Framework: six pillars

Analogy: inspecting a houseWould you buy a house only checking the paint? You check foundations, wiring, locks, running costs and environmental impact too. The framework is that checklist for your cloud design.
PillarCore idea
Operational ExcellenceAutomate, learn from failures, small reversible changes
SecurityLeast privilege, protect data, trace everything
ReliabilityRecover from failure, scale horizontally, test recovery
Performance EfficiencyRight resource type/size, go serverless, experiment
Cost OptimizationPay only for what you use, measure, retire waste
SustainabilityReduce environmental impact: maximise utilisation

Also know the AWS Cloud Adoption Framework (CAF) (people/process/tech view for migrations) and the Well-Architected Tool (a free console tool where you answer questions about your workload).

4. Lab: an alarm that emails you (45 min)

  1. Launch a t3.micro/t2.micro Amazon Linux instance (default VPC is fine).
  2. SNS → Topics → Create (Standard), name cpu-alerts. Create a subscription: protocol Email, your address. Open your email and confirm the subscription.
  3. EC2 → your instance → Monitoring → Manage detailed monitoring (optional, 1-minute metrics). Then CloudWatch → Alarms → Create alarm → Select metric → EC2 → Per-Instance → CPUUtilization for your instance. Statistic Average, period 1–5 min, threshold Greater than 40. Notification: your cpu-alerts topic. Name it high-cpu.
  4. Make the server work hard. Connect with EC2 Instance Connect and run: 
    for i in 1 2; do (while :; do :; done) & done   # burns 2 CPU threads
# later stop it with:  kill %1 %2
  5. Within 5–10 minutes the alarm turns In alarm and an email arrives. Screenshot both. Then kill %1 %2 and watch it return to OK.
  6. Bonus: CloudWatch → Dashboards → create a dashboard with the CPU graph.
  7. Cleanup: delete alarm, SNS topic + subscription, terminate the instance.
