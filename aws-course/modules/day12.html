Protecting Data and Apps: KMS and the Security Toolbox

By the end of today you can Encrypt and decrypt data with a KMS key from the CLI, explain "envelope encryption" simply, and match any security scenario to the right AWS service: Shield, WAF, GuardDuty, Inspector, Macie, Secrets Manager, Cognito, Artifact. This is 30% of the Cloud Practitioner exam.

1. First principles: lock, key, and who holds the key

Encryption scrambles data so it's useless without a key. Two situations: at rest (sitting on a disk or in S3) and in transit (travelling over a network, protected by TLS/HTTPS). The hard part is never the maths. It's protecting the keys.

AWS KMS (Key Management Service) creates and guards your keys inside hardware security modules. You never see the raw key; you ask KMS to encrypt or decrypt, and IAM + key policies decide who may ask. Every use is logged to CloudTrail.

Analogy: the bank safe-deposit roomThe KMS key is the master key kept in the bank vault; it never leaves. You hand the clerk a small box (data) and say "lock this". For big cargo, you use envelope encryption: lock the cargo with a throw-away data key, then ask the bank to lock that small key with the master key. You store the locked cargo and the locked key together. S3, EBS and RDS do exactly this for you.

3. Lab: encrypt something yourself (45 min)

CostA customer managed KMS key costs about US$1/month (pro-rated per hour). Deleting needs a 7-day waiting period, so cost is a few cents. Do the cleanup step at the end.
  1. Create a key: KMS → Customer managed keys → Create key → Symmetric → Alias lab-key → keep you as administrator and user. Finish.
  2. Encrypt from the CLI: 
    echo "my secret plan" > secret.txt
aws kms encrypt --key-id alias/lab-key \
  --plaintext fileb://secret.txt \
  --query CiphertextBlob --output text | base64 --decode > secret.enc
cat secret.enc          # unreadable garbage
aws kms decrypt --ciphertext-blob fileb://secret.enc \
  --query Plaintext --output text | base64 --decode
    You get your sentence back. Notice decrypt never asked which key: the key ID is embedded in the ciphertext.
  3. Prove IAM controls the key: in the key's page, remove yourself from the Key users (or use a limited IAM user). Retry decrypt — AccessDeniedException. Add yourself back.
  4. Encrypt S3 data: create a bucket, Properties → Default encryption → SSE-KMS → choose lab-key. Upload a file, open it: the object details show the KMS key ARN. (SSE-S3 is the free default; SSE-KMS gives audit and control.)
  5. Audit trail: CloudTrail → Event history → filter Event source = kms.amazonaws.com. Find your Encrypt/Decrypt calls. This is why regulators like KMS.
  6. Tour (5 min each, don't enable paid tiers): open GuardDuty, Inspector, Macie and Security Hub consoles and read what the "Get started" page says. Open AWS Artifact and download any report. Read the Shield "Protection" page.
  7. Cleanup: delete the test bucket and objects; KMS → key → Schedule key deletion (7 days). Delete local secret.* files. Don't commit them.

4. Exam notes

Remember
  • Encryption at rest: KMS/S3/EBS. In transit: TLS (ACM certificates).
  • Keys aren't deleted instantly; there's a 7–30 day waiting period. AWS-managed keys rotate yearly automatically; customer-managed rotation is optional.
  • Shield = DDoS. WAF = web exploits. GuardDuty = threat detection. Inspector = vulnerabilities. Macie = sensitive data.
  • Secrets Manager = rotating credentials; Parameter Store = config/secrets, cheaper.
  • Root user: lock away with MFA; use it only for the few tasks that require it.
  • Penetration testing on your own resources is allowed for many services without prior approval (check the policy).
