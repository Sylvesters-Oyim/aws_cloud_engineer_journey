Encryption and Secrets: KMS, ACM, Secrets Manager

By the end of today you can Explain encryption at rest vs in transit, create a KMS key, encrypt an S3 object with it, and prove that a user without key permission is locked out.

1. First principles: if someone steals the box, can they read it?

Security asks three questions: who can get in (IAM, Day 3), what can they do, and if all defences fail, is the data still unreadable? The last one is encryption.

2. KMS: the key vault

KMS (Key Management Service) creates and guards encryption keys. The key never leaves KMS in plain form. Services ask KMS to encrypt/decrypt, and KMS checks IAM permissions first.

Analogy: bank safe-deposit boxesYour files are in the box (S3). The master key stays in the bank's vault (KMS). To open the box you need both: access to the file and permission to use the key. Even an admin of S3 is blocked without key permission.

AWS ownedAWS, invisible to youFree

3. Two more pieces

  • ACM (Certificate Manager): free public TLS certificates that auto-renew, for CloudFront/ALB/API Gateway. You can't download them for use on your own EC2.
  • Secrets Manager: stores database passwords/API keys, encrypted, retrieved at runtime, with automatic rotation (~USD 0.40 per secret/month). Parameter Store (in Systems Manager) is the cheaper option for plain config and simple secrets.

Rule: never put a password in code, an AMI, or Git. Fetch it at runtime with an IAM role.

4. Lab: lock a file behind your own key

Cost safetyA customer managed key costs ~USD 1/month, pro-rated. KMS keys can't be deleted instantly: you schedule deletion (min 7 days). Do it at the end; pennies.
  1. KMS → Create key → Symmetric → alias day12-key. Key administrators: you. Key users: you.
  2. S3 → new bucket day12-enc-YOURNAME-123 → under Default encryption choose SSE-KMS and select day12-key. Upload a text file secret.txt.
  3. Open the object → it shows Server-side encryption: AWS-KMS and your key ARN. Download it: works, because you can use the key.
  4. Break it on purpose: in IAM create a user day12-reader with only the AmazonS3ReadOnlyAccess policy (no KMS rights). Sign in to that user in a private browser window and try to download secret.txt. Result: Access Denied (KMS). S3 permission alone isn't enough.
  5. Fix it by adding that user under the key's Key users, retry: success.
  6. Bonus (CLI): store and read a secret: 
    aws secretsmanager create-secret --name day12/dbpass --secret-string "S3cretPassw0rd!"
aws secretsmanager get-secret-value --secret-id day12/dbpass --query SecretString --output text
aws secretsmanager delete-secret --secret-id day12/dbpass --force-delete-without-recovery
  7. Cleanup: delete the object/bucket, delete the IAM user, schedule key deletion (7 days).

5. Exam notes

Remember
  • Encryption at rest by default: S3 now encrypts all new objects (SSE-S3). Use SSE-KMS for audit and key control.
  • KMS usage is logged in CloudTrail (tomorrow).
  • Passwords → Secrets Manager (rotation) or Parameter Store. Certificates → ACM.
  • CloudHSM = dedicated hardware you control, for strict compliance. KMS = managed and shared hardware.
