By the end of today you can Design the classic web-app layout (public front door, private back rooms), explain why private servers still reach the internet through NAT, and tell Security Groups from Network ACLs, which is one of the most-tested comparisons in both exams.

1. First principles: not everything should face the street

A web server must be reachable. A database must not be. If both sit in public subnets, a single mistake exposes your data. The fix is old as banks: a public lobby, a private vault.

Analogy: a restaurant Customers (internet) meet the waiter in the dining room (public subnet). The kitchen and the safe (private subnet) have no street door. The kitchen still needs deliveries (OS updates), so a NAT gateway acts like a runner who goes out on the kitchen's behalf and brings the parcel back. Strangers can't use the runner to walk in.

2. NAT: outbound yes, inbound no

A NAT gateway sits in a public subnet with an Elastic IP. The private subnet's route table says 0.0.0.0/0 → nat-xxxx. Private instances can start connections out (updates, API calls); the internet cannot start connections in.

NAT gateway is NOT freeAbout USD 0.045 per hour (≈ USD 32/month) plus data charges. For a lab, create it, test it, delete it the same day, and release the Elastic IP.

3. Security Groups vs Network ACLs

Security GroupNetwork ACL (NACL)
ProtectsAn instance (its network interface)A whole subnet
StateStateful: reply traffic is automatically allowedStateless: you must allow the return traffic yourself
RulesAllow onlyAllow and Deny
EvaluationAll rules togetherNumbered, lowest first, first match wins
DefaultDeny all inbound, allow all outboundDefault NACL allows everything
Analogy: building security The NACL is the guard at the estate street entrance with a written list (can say "this person is banned"). The security group is the bouncer at each apartment door who remembers you went out, so lets you back in (stateful). Use SGs for day-to-day; use NACLs for blunt rules like blocking one hostile IP.

Pro move: security groups can reference other security groups as the source. Rule: "database accepts port 3306 only from web-sg". No IP addresses to maintain.

4. Lab: front door + back room (≈ 2 h)

  1. In lab-vpc create a private subnet lab-private-a (AZ a, 10.0.11.0/24). Do not enable auto-assign public IP.
  2. Create a new route table lab-private-rt (no internet route yet) and associate it with lab-private-a. Notice it only has the local route.
  3. Create lab-app-sg: inbound HTTP 80 with source = lab-web-sg (pick the SG, not an IP). No SSH.
  4. IAM role for no-key access: IAM → Roles → Create → EC2 → attach AmazonSSMManagedInstanceCore → name lab-ssm-role. This lets you open a shell from the console (Session Manager), so the private server needs no SSH port and no key.
  5. Launch lab-private-server in lab-private-a, SG lab-app-sg, no public IP, instance profile lab-ssm-role. Also relaunch your lab-web public instance from Day 8 (same settings as before).
  6. Prove it is isolated: try Systems Manager → Session Manager → Start session on the private server. It won't appear yet: it has no path to the SSM service. That is the point of the next step.
  7. Create the NAT gateway: VPC → NAT gateways → Create, subnet lab-public-a (it must live in a public subnet), connectivity Public, Allocate Elastic IP. Wait for "Available".
  8. Edit lab-private-rt: add 0.0.0.0/0 → NAT gateway. Wait ~2 minutes, then connect with Session Manager (or reboot the instance if it still doesn't show).
  9. In that shell run: 
    curl -s https://checkip.amazonaws.com    # shows the NAT gateway's Elastic IP, not a server IP
sudo dnf install -y nginx && echo private-ok | sudo tee /usr/share/nginx/html/index.html && sudo systemctl start nginx
  10. From the public web instance (SSH or Session Manager) run curl http://PRIVATE-IP. It works because lab-app-sg trusts lab-web-sg. From your laptop's browser the same private IP is unreachable. 🎯
  11. Stretch (NACL): in the default NACL of the VPC add a Deny rule #90 for inbound TCP 80 from your own IP and watch your public page stop loading. Delete the rule to restore.
  12. CLEANUP, do it now: terminate both instances, delete the NAT gateway, wait until Deleted, then Release the Elastic IP (VPC → Elastic IPs). Billing → check no NAT is listed.

5. Exam notes

Remember
  • Private instance needs internet for updates → NAT gateway in a public subnet, route from the private subnet.
  • NAT gateway = managed, per-AZ, hourly cost. Put one per AZ for resilience.
  • Security group = stateful, allow-only, instance level. NACL = stateless, allow+deny, subnet level.
  • To block one malicious IP address, use a NACL deny rule (security groups can't deny).
  • Reach AWS services without internet or NAT: VPC endpoints (Gateway endpoints for S3 and DynamoDB are free).

6. Quiz

Q1. A private EC2 needs to download patches but must not be reachable from the internet. Solution?NAT gateway in a public subnet + route 0.0.0.0/0 → NAT in the private route table.
Q2. Which firewall is stateless?Network ACL.
Q3. You must block traffic from one abusive IP at the subnet. Which tool?A NACL deny rule.
Q4. Where does a NAT gateway live?In a public subnet (with an Elastic IP).
Q5. Database should accept connections only from web servers. Best practice?Security group rule whose source is the web tier's security group.
Q6. How can an instance in a private subnet reach S3 privately and for free?S3 gateway VPC endpoint.
