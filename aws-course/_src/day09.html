1. Two layers of firewall

Analogy: a hotel The NACL is the guard at the hotel's front gate checking everyone entering and leaving the street (subnet level). The security group is the lock on each room door (instance level). The room lock remembers guests: if you let someone in, they can walk out freely (stateful). The gate guard keeps no memory, so every direction needs its own rule (stateless).

In practice: use security groups for 95% of work. Reach for a NACL when you need an explicit deny, for example blocking one abusive IP range.

3. NAT: outbound-only internet

Your private database server still needs to download patches. But it must not be reachable from outside. A NAT Gateway sits in a public subnet; private subnets route 0.0.0.0/0 to it. Requests go out, replies come back, nobody can start a connection inbound.

Analogy: company switchboardStaff make outside calls through the switchboard; callers see only the company number and cannot dial a staff member's desk directly.
NAT costs real moneyA NAT Gateway bills per hour (about USD 0.045/hr, roughly USD 32/month) plus per GB. Create it, test it, delete it in the same session. Release its Elastic IP afterwards.

4. Lab

Part A: security group chaining

  1. EC2 → Security groups → create web-sg in lab-vpc: inbound HTTP 80 from 0.0.0.0/0, SSH 22 from My IP.
  2. Create db-sg: inbound Custom TCP 3306, source = the web-sg security group (type its name, don't use an IP).
  3. Read the two groups side by side and explain out loud who can reach the database. Only web-sg members.

Part B: private instance + NAT

  1. Launch a second EC2 in private-a with no public IP, security group db-sg. Use EC2 Instance Connect Endpoint or Session Manager (attach the AmazonSSMManagedInstanceCore role) to get a shell without opening SSH. If that's fiddly, SSH via your public instance as a jump box.
  2. In the shell run curl -m 5 https://example.com. It times out: there is no route out.
  3. VPC → NAT gateways → Create: subnet public-a, connectivity public, Allocate Elastic IP.
  4. Route tables → create private-rt: 0.0.0.0/0 → the NAT gateway. Associate with private-a.
  5. Re-run the curl. It now works. From your laptop you still can't reach this instance. Outbound only. That's the design.
  6. Cleanup now: delete the NAT gateway, wait until "Deleted", then release the Elastic IP. Remove the private-rt NAT route. Stop the instances.

Part C: NACL deny

  1. Network ACLs → create lab-nacl, associate with public-a. Notice a brand-new custom NACL denies everything.
  2. Add inbound rule 100 allow HTTP 80 from 0.0.0.0/0, outbound rule 100 allow custom TCP 1024–65535 to 0.0.0.0/0 (the return traffic). Browse your public instance: works.
  3. Add inbound rule 90 deny HTTP from your own IP /32. Rule 90 is checked before 100, so you are blocked. Delete it and you're back.

5. Exam notes

Remember
  • Security group = stateful, allow-only, instance level. NACL = stateless, allow + deny, subnet level.
  • NAT Gateway: private subnet → internet, outbound only. Lives in a public subnet, is AZ-scoped (one per AZ for resilience).
  • "Block a specific IP" almost always means a NACL (or WAF for web traffic).
  • Bastion host / Session Manager: ways to administer private instances.

6. Quiz

Q1. You must explicitly deny one malicious IP range at the subnet. What?Network ACL deny rule.
Q2. Private instances need OS updates but no inbound access. What?NAT Gateway in a public subnet + route from the private subnet.
Q3. You allowed inbound 80 on a security group. Do you also add an outbound rule for replies?No. Security groups are stateful.
Q4. Custom NACL just created: what traffic does it allow?None. It denies everything until you add rules (the default NACL allows all).
Q5. Best way to allow only the app tier to hit the database?DB security group with the app security group as the source.
