By the end of today you can Explain what a CDN does, put CloudFront in front of a private S3 bucket, get HTTPS for free, and clear the cache.

1. First principles: distance is latency

Light is fast, but a request from Nairobi to a server in Virginia still takes ~250 ms round trip, many times over for a page full of images. The fix is to keep copies close to users. A CDN (Content Delivery Network) does exactly that, and CloudFront is AWS's CDN, with hundreds of edge locations worldwide.

Analogy: a newspaperThe printing press (your origin, e.g. S3) is in one city. Instead of everyone fetching from it, copies are delivered to corner shops (edge locations). First customer of the day causes a delivery (cache miss); everyone after buys from the shelf (cache hit). TTL is how long before the shop discards the old paper.

Benefits: lower latency, less load on the origin, free HTTPS (certificate from ACM), and built-in protection (AWS Shield Standard; WAF can be attached). Origins can be S3, an ALB, an EC2 or any web server.

2. Lab: private S3 website, global and HTTPS

This upgrades your Day 6 website: the bucket stays private, and only CloudFront may read it using Origin Access Control (OAC).

  1. Create a new bucket yourname-cdn-lab-12345, keep Block Public Access ON. Upload index.html (any page, add a heading and an image).
  2. CloudFront → Create distribution. Origin domain: pick your S3 bucket. Origin access: Origin access control settings (recommended) → create control. Default root object: index.html.
  3. Viewer protocol policy: Redirect HTTP to HTTPS. WAF: choose the cheaper "do not enable" option for the lab. Create.
  4. CloudFront shows a banner with a bucket policy: Copy policy → open the bucket → Permissions → Bucket policy → paste → Save.
  5. Wait for status Deployed (2 to 5 minutes). Open https://dxxxxxxxx.cloudfront.net. Your page loads over HTTPS from a private bucket.
  6. Prove it's private: try the direct S3 object URL. AccessDenied. Only CloudFront gets in.
  7. Watch the cache: 
    curl -sI https://dxxxxxxxx.cloudfront.net/ | grep -i x-cache
    First time Miss from cloudfront, second time Hit from cloudfront.
  8. Edit index.html and re-upload. The old content still shows (cached). Distribution → Invalidations → Create with path /*. Refresh: new content. (The first 1,000 invalidation paths a month are free.)
  9. Cleanup: Disable the distribution, wait, then Delete. Empty and delete the bucket.
📸 Evidence: evidence/day11-cloudfront-https.png (padlock visible) and the Hit/Miss headers.

Custom domain bonus (if you did Day 10): request a certificate in ACM in us-east-1 (required for CloudFront), add the domain as an alternate name on the distribution, then create a Route 53 Alias record to it.

3. Exam notes

Remember
  • CloudFront = CDN, global edge locations, caches content, reduces latency. Pricing: pay per request and data out; data from S3 to CloudFront is free.
  • OAC keeps S3 private. The old way (OAI) is legacy; OAC is current.
  • CloudFront certificates must be requested in us-east-1.
  • Dynamic and static content both work; use TTL and invalidations to control freshness.
  • Don't confuse: CloudFront caches content at the edge; Global Accelerator speeds up TCP/UDP traffic over the AWS backbone with static anycast IPs (no caching).

4. Quiz

Q1. Global users complain about slow image loads from an S3 bucket in one Region. Fix?Put CloudFront in front of the bucket.
Q2. How do you keep the S3 bucket private but let CloudFront read it?Origin Access Control plus a bucket policy for the distribution.
Q3. You updated a file but visitors still see the old one. Quick fix?Create an invalidation (or use versioned filenames).
Q4. Which Region must hold an ACM certificate for CloudFront?us-east-1 (N. Virginia).
Q5. CloudFront vs Global Accelerator?CloudFront caches content; Global Accelerator routes traffic over AWS's network to the best endpoint, no caching.
